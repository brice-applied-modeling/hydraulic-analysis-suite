# HAS Engineering Verification Plan

**Project:** Hydraulic Analysis Suite (HAS)  
**Document:** `docs/engineering/09_verification_plan.md`  
**Status:** Engineering verification framework; implementation-dependent results pending  
**Applies to:** Python 3.12, hydraulic calculations, design checks, and future integrated models

## 1. Purpose

This plan defines how HAS engineering calculations will be independently verified, documented, reviewed, and maintained. Verification establishes that a numerical implementation correctly solves its stated engineering equations within defined assumptions and tolerances. Validation, where field or experimental evidence is available, separately assesses whether the model adequately represents a real system.

A passing automated test alone does not demonstrate engineering correctness when its expected value was generated by the same implementation under test.

## 2. Scope and maturity

Verification is required for implemented functionality before it is described as verified. Planned modules remain **NOT IMPLEMENTED** or **NOT VERIFIED** until objective evidence exists.

| Domain | Representative verification targets | Dependency |
|---|---|---|
| Units and constants | gpm↔ft³/s, inches↔feet, psi↔feet of fluid, power | Unit conventions and reference constants |
| Pipe hydraulics | Area, velocity, Reynolds number, friction factor, major head loss | Pipe implementation |
| Fittings | K values, velocity basis, minor head loss, aggregation | Fitting implementation |
| Force main | Static head, boundary HGL, total head, system curve, pressure profile | Pipe and fitting calculations |
| Pump | Curve interpolation, pump/system intersection, efficiency, BHP | Pump implementation and manufacturer data |
| Wet well | Volume, elevations, fill/drawdown time, cycling | WetWell and controls |
| Operating scenarios | Boundary combinations, parallel pumps, firm capacity | Integrated models |
| Design checks | PASS/WARNING/FAIL/NOT_EVALUATED/NOT_APPLICABLE | Verified calculation outputs and criteria |
| Transient screening | Joukowsky estimate, travel time, pressure limits, validity flags | Screening implementation |

This plan does not claim that any listed module is complete.

## 3. Verification principles

1. **Independence:** Derive expected values by hand, an independently authored spreadsheet, published analytical example, manufacturer data, or a suitably configured independent engineering model. Do not merely reuse HAS functions to calculate expected values.
2. **Traceability:** Record the governing equation, reference edition/page or manufacturer curve, assumptions, units, input values, expected outputs, and evidence.
3. **Reproducibility:** A case must be rerunnable with recorded input data, code revision, environment, and deterministic settings.
4. **Dimensional consistency:** Validate conversions and physical units at interfaces; use explicit U.S. customary or SI conventions as applicable.
5. **Boundaries and invalid inputs:** Include zero, near-zero, limiting, and invalid values; reject physically impossible inputs rather than silently producing misleading results.
6. **Separation:** Keep verification of the mathematical implementation separate from validation of physical-system assumptions.
7. **Conservative reporting:** Never convert an unperformed check, missing source, or inapplicable equation into a PASS.

## 4. Verification levels

### V0: Reference and requirements audit

Verify engineering source, applicability, edition, assumptions, and unit basis. Document conflicts between owner criteria, manufacturer limits, and general references.

### V1: Unit and component verification

Test isolated calculations against independently derived values, including analytical edge cases and dimensional checks.

### V2: Coupled hydraulic verification

Verify calculations across components, including pipe + fittings, force-main boundaries, and pump/system operating points. Check conservation of mass and energy and numerical solution residuals.

### V3: Scenario and design-check verification

Verify scenario isolation, governing-case selection, limit comparisons, and consistent status classification. Explicitly test equality at thresholds and missing criteria.

### V4: External-model comparison or field validation

Where appropriate, compare against EPANET, WaterGEMS, SewerGEMS, specialized transient software, or field observations. Document differences in boundary conditions, loss methods, curve definitions, numerical settings, and model scope. Agreement is evidence, not automatic proof.

## 6. Acceptance criteria and tolerances

### 6.1 General numerical comparison

For expected value $E$ and actual value $A$:

$$
\Delta_{abs}=|A-E|
$$

$$
\Delta_{rel}=\frac{|A-E|}{|E|},\quad E\ne 0
$$

A numerical comparison passes when:

$$
|A-E|\leq ATOL+RTOL|E|
$$

The combined rule accommodates values near zero without dividing by an arbitrarily small reference. Record actual residuals and tolerance values in each case.

### 6.2 Provisional software-verification tolerances

The following are **starting targets for deterministic calculations**, not regulatory design allowances or universal requirements. Confirm suitability for each algorithm and reference precision.

| Calculation class | Initial target | Qualification |
|---|---|---|
| Exact unit conversions and basic geometry | `RTOL = 1e-10`, `ATOL = 1e-12` in output units | Use exact defined factors where practical; account for floating-point representation |
| Closed-form hydraulic calculations | `RTOL = 1e-8`, `ATOL` set for output scale | Tighten or relax with documented numerical rationale |
| Iterative friction-factor and operating-point solvers | `RTOL = 1e-6`, scale-aware `ATOL` | Also verify governing-equation residual and solver convergence |
| Published worked examples | Case-specific | Match source precision, rounding, assumptions, and source uncertainty |
| External-model comparisons | Case-specific | Document model formulation, boundary and parameter differences |
| Design-check threshold logic | Exact logical result at specified boundary | Do not introduce tolerance-based status changes without a documented policy |

**Never use a generic percentage tolerance to conceal a wrong equation, inconsistent units, or different boundary conditions.** A calculation can meet a numerical tolerance and still be physically invalid.

### 6.3 Engineering criteria versus software tolerance

A project velocity limit, NPSH margin, allowable pressure, or pump operating range is an **engineering criterion**, not a numerical accuracy tolerance. Store the criterion source and compare against the computed result using an explicit rule. Missing criteria produce `NOT_EVALUATED`, not `PASS`.

## 7. Required verification cases

### 7.1 Units, constants, and material data

- Verify U.S. gallons versus Imperial gallons and conversion factors.
- Check diameter and area unit handling, including nominal versus actual internal diameter.
- Distinguish fluid mass density, specific weight, and specific gravity.
- Verify viscosity units and temperature applicability.
- Audit material properties and fitting coefficients against their sources and ranges.

### 7.2 Pipe and fitting hydraulics

- Verify $Q=AV$, Reynolds number, laminar $f=64/Re$, and turbulent friction-factor method against independent values.
- Verify Darcy–Weisbach major loss and $h_m=K V^2/(2g)$ minor loss.
- Test zero flow, small flow, roughness limits, diameter changes, and invalid inputs.
- Confirm that minor-loss velocity references correspond to the correct local pipe section.

### 7.3 Force-main hydraulics

- Verify wet-well surface and downstream HGL as distinct hydraulic boundaries.
- Verify static head and friction losses with consistent datum and exit-loss conventions.
- Check HGL and pressure at representative pipeline stations.
- Test minimum/maximum wet-well levels and downstream HGL conditions.
- Verify monotonic behavior where assumptions warrant it, without assuming friction is exactly proportional to $Q^2$ across all regimes.

### 7.4 Pumps and system curves

- Independently verify pump curve interpolation within documented bounds; handle extrapolation explicitly.
- Verify pump/system intersection and residual $H_{pump}(Q)-H_{system}(Q)$.
- Verify efficiency and brake horsepower with appropriate fluid properties.
- Verify parallel pump combinations at common head, including branch losses when present.
- Check NPSHA/NPSHR definitions and reference planes; do not treat NPSH3 as cavitation-free operation.

### 7.5 Wet wells and controls

- Verify circular/rectangular storage volumes and elevation-storage relationships.
- Verify constant-inflow filling, drawdown, starts per hour, and the $Q_{in}=Q_p/2$ maximum cycling condition under stated assumptions.
- Test $Q_{in}\geq Q_p$, zero inflow, and minimum run/off-time rules.
- Verify lead/lag events and volume conservation in any time-dependent simulation.

### 7.6 Operating scenarios and design checks

- Verify each scenario changes only its specified inputs.
- Check pump-unavailable and firm-capacity scenarios using the actual hydraulic operating point.
- Verify minimum and maximum velocity, pump POR/AOR, NPSH margin, motor loading, and capacity comparisons.
- Test PASS, WARNING, FAIL, NOT_EVALUATED, and NOT_APPLICABLE with boundary and missing-data cases.

### 7.7 Transient screening

- Verify $|\Delta H|=a|\Delta V|/g$ and $T_r=2L/a$ independently.
- Verify pressure/head conversions and absolute versus gauge pressure.
- Flag predicted single-phase pressures at or below vapor pressure as **outside the model's physical applicability**.
- Do not claim that screening predicts actual pump-trip extrema, check-valve slam, or complete transient safety.

## 8. Verification procedure

For each case:

1. Assign a unique ID and identify the engineering requirement.
2. Record the implementation and applicable operating assumptions.
3. Select an independent reference method and document its source.
4. Define inputs, units, initial conditions, and expected results before evaluating HAS output.
5. Run the implementation and capture actual results and software revision.
6. Compare results using the case-specific tolerance and physical validity checks.
7. Document discrepancies, suspected causes, and corrective actions.
8. Assign case status and reviewer disposition.
9. Link the case record to the corresponding automated test, issue, or commit.
10. Re-run affected cases after relevant code, data, or criteria changes.

## 9. Failure and exception handling

Use the following verification statuses, separate from design-check statuses:

- **NOT RUN:** Case defined but not executed.
- **PASS:** Independent reference and acceptance conditions satisfied.
- **FAIL:** Result or required behavior does not satisfy the case.
- **BLOCKED:** Required implementation, data, or external reference unavailable.
- **INCONCLUSIVE:** Comparison performed but uncertainty or mismatch prevents a defensible conclusion.
- **NOT APPLICABLE:** Case does not apply to the implemented configuration.

Do not mark a case PASS solely because a test executed without throwing an exception. Document known limitations and deviations explicitly.

## 10. Regression and change control

Re-run impacted verification cases when changes affect:

- Hydraulic equations, solvers, or numerical settings.
- Constants, conversion factors, material or fitting reference data.
- Pump curves, boundary conditions, or component interfaces.
- Criteria thresholds or classification logic.
- Serialization, output units, or reporting.

Retain the case ID, update revision metadata, and document whether the expected value or acceptance criterion changed and why. An expected-value change must have independent justification.

## 11. Verification evidence and reporting

Each completed case must include:

- Input dataset and units.
- Reference calculation or source citation.
- Expected and actual values.
- Absolute/relative error or solver residual as appropriate.
- Applicable tolerances and physical checks.
- Software revision and environment.
- Test execution reference.
- Reviewer, date, status, and unresolved limitations.

Use `docs/verification/templates/case_result_template.md` as the standard case record.

## 12. Release gates

A capability may be labeled **engineering-verified for its documented scope** only when:

1. Its governing methods and limitations are documented.
2. Required unit/component cases pass with independent references.
3. Applicable boundary, invalid-input, and integration cases pass.
4. No unresolved high-consequence failures remain in its stated scope.
5. Verification evidence is reproducible and tied to a code revision.
6. Remaining exclusions and uncertainties are disclosed.

Verification does not constitute regulatory approval, design certification, or validation for every real-world system.

## 13. Initial implementation priorities

1. Audit constants and conversions.
2. Establish independent pipe and fitting calculation cases.
3. Verify force-main energy balance and boundary conditions.
4. Add pump curve and operating-point cases once implemented.
5. Extend to wet-well, scenario, design-check, and transient-screening cases as their modules become available.
